# Contributing to Finkkle

Thanks for wanting to help out. Whether it's a bug report, a fix, an idea, or a typo in the docs, it all counts.

This guide covers the basics. Some repos have their own rules, so if a project has its own CONTRIBUTING file, that one wins.

---

## Before you start

**Check whether the repo is open to contributions.** Not every Finkkle project accepts outside changes. The repo's README will say what it is, where it's at, and whether we're taking pull requests.

**Look for an existing issue.** Someone may already be on it, or we may have talked it through before. A quick search saves everyone time.

**For anything bigger than a small fix, open an issue first.** Tell us what you'd like to change and why. We'd hate for you to spend a weekend on something we can't merge, and a short conversation up front usually leads to a better result anyway.

---

## Reporting a bug

A good bug report lets us reproduce the problem without guessing. Please include:

- What you expected to happen
- What actually happened
- Steps to reproduce it, as short as you can make them
- Your environment: device, OS, app or package version, browser if relevant
- Screenshots, logs, or error messages if you have them

If you're not sure whether something is a bug, open an issue anyway. We'd rather hear about it.

---

## Suggesting an idea

We love hearing how people want to use what we build. When you suggest a feature, tell us about the problem you're trying to solve, not just the solution you have in mind. Knowing *why* helps us find the right fit, even if it ends up looking a bit different from what you pictured.

---

## Making a change

1. **Fork the repo** and create a branch from the default branch. Give it a name that says what it does, like `fix-login-timeout` or `docs-setup-guide`.
2. **Keep it focused.** One pull request, one change. Small PRs get reviewed faster and are easier to merge.
3. **Follow the existing style.** Match the conventions you see in the code around you. If the repo has a linter or formatter, run it.
4. **Test your work.** Add or update tests where it makes sense, and make sure the existing ones still pass.
5. **Update the docs** if your change affects how something works or is used.
6. **Write clear commit messages.** A short summary line, plus a bit more detail if the change needs explaining.

---

## Opening a pull request

In your PR description, tell us:

- What the change does
- Why it's needed (link the related issue if there is one)
- How you tested it
- Anything you're unsure about or would like a second opinion on

Then sit back. We'll review it as soon as we can. We might ask questions or suggest changes. That's a normal part of the process, not a sign anything's wrong. Once it's ready, we'll merge it and say thanks.

---

## Security issues

Please **don't** report security vulnerabilities in a public issue. Get in touch privately through [support.finkkle.com](https://support.finkkle.com) instead, so we can fix the problem before it's widely known.

---

## Be kind

We want this to be a friendly place to work. Be respectful, assume good intent, and give feedback the way you'd like to receive it. Harassment or personal attacks aren't welcome here.

---

## Questions?

If something in this guide is unclear, or you're not sure where to start, open a discussion in the relevant repo or reach out through [support.finkkle.com](https://support.finkkle.com).

Thanks again for helping make Finkkle better.
